# ADR-0007: 认证与授权

- **Status**: Accepted
- **Date**: 2026-08-29
- **Phase**: Phase 1
- **Supersedes**: None
- **Superseded by**: None

## Context

需要确定：access token 形态、refresh token 形态与存储、签名算法、
密码哈希算法、RBAC 的表达方式。

安全需求：可撤销、可轮转、可检测盗用、不泄漏用户存在性、抗暴力破解。

## Decision

### 总体：短期 JWT access token + opaque refresh token

| | Access Token | Refresh Token |
|---|---|---|
| 形态 | JWT (HS256) | 256 位随机串，Base64URL |
| TTL | **15 分钟** | **30 天** |
| 存储 | 不存（无状态） | PostgreSQL，**存 SHA-256 哈希** |
| 撤销 | 不可（靠短 TTL 收敛） | 可，立即生效 |
| 传输 | `Authorization: Bearer <token>` | 请求体 |

#### 为什么 access token 无状态

每个请求都查一次数据库验证 session，会让认证成为所有接口的共同瓶颈，
并使水平扩容依赖共享存储的可用性。JWT 让验证变成一次本地签名校验。

**代价明确写在这里**：access token 在签发后 15 分钟内无法撤销。
用户改密码或被封禁后，最长有 15 分钟的窗口期旧 token 仍然有效。

三种缓解方案的取舍：

1. 引入 Redis 黑名单 → 又回到"每请求一次远程查询"，抵消了无状态的意义
2. 缩短 TTL 到 1-2 分钟 → 刷新请求量激增
3. **接受 15 分钟窗口**（选中），并在**高危操作**（改密码、改邮箱、删除账号）
   上额外要求重新认证，而不是依赖 token 撤销

> **When to Revisit**：出现监管要求"封禁必须秒级生效" → 引入 Redis 黑名单，
> 只对被封禁用户写入（数量小，查询可用布隆过滤器前置）。

#### 为什么 refresh token 是 opaque 而非 JWT

JWT refresh token 无法撤销，与 refresh token 的**全部意义**（长期有效 + 可撤销）矛盾。
既然必须存储才能撤销，就没有理由再用 JWT ——
opaque 随机串更短、不泄漏任何信息、验证逻辑更简单。

#### 为什么 refresh token 用 SHA-256 而不是 bcrypt/Argon2

refresh token 是**服务端生成的 256 位高熵随机值**，不是低熵人类密码。
慢哈希的目的是抵抗离线字典攻击，而 256 位随机值不存在字典。
用 bcrypt 只会给每次刷新请求增加 ~100ms 且无安全收益。

**存哈希而非明文**的目的是：数据库泄漏时攻击者无法直接用这些值冒充用户。

### Refresh Token 轮转与盗用检测

```text
POST /auth/refresh { refresh_token }
      │
      ├─ 查 sha256(token) 对应的 session
      │
      ├─ 不存在              → 401 invalid_grant
      ├─ 已过期              → 401 invalid_grant
      ├─ 已被撤销 (revoked)  → ★ 盗用信号
      │      └─ 撤销整个 family 的所有 session（强制该用户全部设备重新登录）
      │         记录安全事件日志 + 指标
      │         → 401 invalid_grant
      │
      └─ 有效 → 【事务】
                 标记旧 session revoked_at = now(), 
                 插入新 session（同 family_id，parent = 旧 id）
                 提交
              → 返回新的 access + refresh
```

`refresh_sessions` 表关键列：

```text
id            uuid  PK
user_id       uuid  FK → users(id) ON DELETE CASCADE
token_hash    bytea UNIQUE NOT NULL       -- sha256
family_id     uuid  NOT NULL              -- 一次登录 = 一个 family
parent_id     uuid  NULL                  -- 轮转链
expires_at    timestamptz NOT NULL
revoked_at    timestamptz NULL
created_at    timestamptz NOT NULL
user_agent    text NULL                   -- 仅用于"我的登录设备"展示
ip            inet NULL
```

**盗用检测的原理**：正常客户端拿到新 token 后就不会再用旧的。
如果一个已轮转（revoked）的 token 再次被使用，说明它被复制过——
此时无法判断是攻击者还是真实用户先用，安全的做法是**撤销整个 family**。

这个机制是本设计中"值得的复杂度"：它只需要两个额外列，
就把 refresh token 泄漏从"长期静默入侵"降级为"最多一次使用即被发现"。

**轮转必须在事务中**（ADR-0005 的第一个真实事务用例）。

### 登出

```text
POST /auth/logout  { refresh_token }  →  撤销该 token 所在的整个 family
```

即"登出当前设备"。Access token 不受影响，最多 15 分钟后自然失效。

预留但 v1 不做：`POST /auth/logout-all`（撤销该用户全部 family）。

### JWT 细节

Claims：

```json
{
  "iss": "goscaffoldforlevi",
  "sub": "<user uuid>",
  "aud": "goscaffoldforlevi-api",
  "iat": 1756...,
  "exp": 1756...,
  "jti": "<uuid v7>",
  "role": "admin"
}
```

- `jti` **必须有**，即使 v1 不做黑名单——它让日志中可以追踪单个 token 的使用
- `role` 放进 claims 是有意的：避免每个请求查库取角色。
  代价是**改角色后最多 15 分钟才生效**，与撤销窗口一致，可接受
- **不放** email、name 或任何 PII —— JWT 是 Base64 而非加密，客户端和中间设备都能读

算法：**HS256**，密钥 ≥ 32 字节，从环境变量注入，启动时校验长度。

选 HS256 而非 RS256/EdDSA 的理由：v1 只有一个服务同时负责签发和验证，
对称密钥少一套密钥管理。签发/验证封装在 `auth.TokenIssuer` / `auth.TokenVerifier`
接口后，换非对称算法只需替换实现。

> **When to Revisit**：出现第二个需要独立验证 token 的服务 → 换 EdDSA（Ed25519），
> 公钥可安全分发，并考虑 JWKS 端点。

**业务 Service 不直接依赖 JWT 库**：`auth` 包定义接口，
具体实现（`golang-jwt/jwt/v5`）在实现文件中，可替换。

### 密码哈希

**Argon2id**（`golang.org/x/crypto/argon2`）。

参数（可通过配置调整，默认值面向 2026 年硬件）：

```text
time   = 3
memory = 64 MB
threads = 4
saltLen = 16 B
keyLen  = 32 B
```

编码格式使用标准的 PHC 字符串：`$argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>`，
参数随哈希一起存储，从而**可以在不迫使用户改密码的情况下升级参数**
（登录成功时若发现参数低于当前配置，就用新参数重新哈希）。

选 Argon2id 而非 bcrypt 的理由：

- bcrypt 有 **72 字节输入截断**问题，长密码或含多字节字符的密码会被静默截断
- bcrypt 只吃 CPU，对 GPU/ASIC 攻击的抵抗弱于 memory-hard 的 Argon2id
- Argon2id 是 OWASP 当前的首选推荐

代价：每次登录消耗 64 MB 内存 × 并发数。
必须与限流配合（ADR-0008 对 login 有独立严格限流），
否则登录接口本身就是内存耗尽型 DoS 的入口。**这是一个必须同时落地的组合。**

其他要求：

- 验证使用库提供的常量时间比较
- 用户不存在时**仍然执行一次哈希运算**（对固定的假哈希），
  否则响应时间差异会泄漏邮箱是否注册
- 密码策略：最短 12 字符，最长 128（防 DoS），不做强制字符类别要求
  （NIST SP 800-63B 建议长度优先于复杂度规则）

### 登录的信息泄漏防护

```text
邮箱不存在  → 401 { code: "INVALID_CREDENTIALS", message: "invalid credentials" }
密码错误    → 401 { code: "INVALID_CREDENTIALS", message: "invalid credentials" }
账号被禁用  → 401 { code: "INVALID_CREDENTIALS", message: "invalid credentials" }
```

三种情况**响应体、状态码、响应时间**都必须一致。

注意第三条：把"账号已禁用"单独返回 403 会泄漏"这个邮箱存在且被禁用"。
被禁用用户的申诉路径应通过其他渠道，不通过登录接口的错误信息。

**注册接口存在同样的泄漏面**：`POST /users` 返回 409 "email taken" 就等于确认了
该邮箱已注册。v1 接受这个泄漏（管理员创建用户的场景需要明确反馈），
但在 `docs/security.md` 中记录；若将来开放公开自助注册，
必须改为"总是返回 202 + 发确认邮件"。

### 认证中间件

```go
// 放入 context 的内容，仅此两项
type Principal struct {
    UserID uuid.UUID
    Role   Role
}
```

**不把完整 User 对象放进 context**：那会诱使 handler 直接使用 context 里的
陈旧数据、隐藏数据来源、并让 context 成为隐式的数据传递通道。
需要完整用户就显式调 Service。

context key 未导出，通过 `auth.PrincipalFrom(ctx) (Principal, bool)` 读取。

### 授权（RBAC）

角色：`admin`、`user`。

**集中式策略表**，`internal/auth/policy.go`：

```go
type Permission string

const (
    PermUserCreate  Permission = "user:create"
    PermUserRead    Permission = "user:read"     // 任意用户
    PermUserList    Permission = "user:list"
    PermUserUpdate  Permission = "user:update"   // 任意用户
    PermUserDelete  Permission = "user:delete"
)

var rolePermissions = map[Role][]Permission{
    RoleAdmin: {PermUserCreate, PermUserRead, PermUserList, PermUserUpdate, PermUserDelete},
    RoleUser:  {}, // 普通用户没有"对任意用户"的权限
}

func (r Role) Can(p Permission) bool
```

两类授权规则，分开表达：

1. **角色权限**：中间件 `RequirePermission(PermUserList)` 挂在路由上
2. **所有权**：`user` 只能读写自己 → 在 Service 层用统一 helper：
   ```go
   func AuthorizeSelfOrPermission(p Principal, targetID uuid.UUID, perm Permission) error
   ```

为什么所有权检查放 Service 而非中间件：中间件拿不到"目标资源属于谁"
（有时需要先查库）。放 Service 保证无论从哪个入口进来都会被检查。

**明确禁止**：`if role == "admin"` 出现在 handler 或 service 中。
Phase 8 会 grep 审计。

## Consequences

### 正面

- 认证无远程依赖，扩容不受限
- refresh token 可撤销、可轮转、能检测盗用
- 密码哈希参数可平滑升级
- 权限规则集中在一个文件，可审计、可测试
- 登录不泄漏用户存在性

### 负面 / 代价

- access token / 角色变更有最长 15 分钟的生效延迟
- Argon2id 每次登录消耗 64 MB 内存，**强依赖登录限流**
- refresh 轮转需要事务，且客户端必须正确保存新 token（否则会被判为盗用）
- 移动端弱网重试可能触发误判 family 撤销 → 需在客户端 SDK 中保证刷新请求不并发重试
- HS256 意味着密钥泄漏即可伪造任意 token，密钥管理是单点

### 后续影响

- Phase 3 实现全部上述内容，含 `refresh_sessions` 表
- Phase 3 必须与 ADR-0008 的登录限流同时落地（Argon2id 的前提）
- Phase 5 需要 `login_total` / `login_failure_total` / `refresh_reuse_detected_total` 指标
- Phase 8 安全审计：grep `role ==`、检查日志不含 token、验证登录时序一致

## Alternatives Considered

| 方案 | 优点 | 缺点 | 未选择的原因 |
|------|------|------|--------------|
| 纯服务端 Session（Cookie + Redis） | 立即可撤销、最简单 | 每请求一次 Redis、跨域/移动端体验差 | 目标场景含 SPA/移动/B2B 集成 |
| JWT refresh token | 无需存储 | 无法撤销 | 与 refresh 的目的矛盾 |
| 不做轮转，refresh 长期有效 | 实现简单 | 泄漏后长期静默滥用 | 安全性不足 |
| bcrypt | 库成熟、无内存压力 | 72 字节截断、抗 GPU 弱 | OWASP 已不作首选 |
| Casbin | 策略灵活、支持 ABAC | 引入 DSL 与策略存储，v1 只有 2 个角色 | 过度设计 |
| 权限写在数据库 | 运行时可改 | 每请求查库、需要管理界面 | v1 角色固定，YAGNI |

## When to Revisit

- 需要秒级封禁 → 加 Redis 黑名单
- 出现第二个验证方服务 → 换 EdDSA + JWKS
- 角色超过 5 个或出现资源级细粒度权限 → 评估 Casbin 或自建策略存储
- 开放公开自助注册 → 必须先改造注册接口的用户枚举防护
